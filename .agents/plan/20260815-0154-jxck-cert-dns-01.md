blocker 0、major 3、minor 3。`reconfigure` -> force renewal -> `h2o -t` -> reload -> live 確認の

### Findings

1. **major: SAN 数と propagation-seconds の因果を訂正する**
   - この VPS の Certbot 5.7.0 `dns_common.py` は全 challenge の TXT record を順に作成した後、
     challenge 数によらず `dns_cloudflare_propagation_seconds` だけ **1 回** sleep してから全 response を
     返す。したがって 18 SAN であること自体は、7 SAN より長い伝播待ち時間を必要とする根拠にならない。
   - 18 SAN では Cloudflare API の create / cleanup 呼び出しと ACME validation の対象が増え、全体の
     実行時間と部分失敗の表面積は増える。一方、各 TXT record は最後の record を作成した後から同じ
     30 秒を確保されるため、「SAN が多いほど NXDOMAIN が起きやすい」「30 秒よりさらに余裕を持たせる」
     という tldr / 現状 / リスクの説明は分離する必要がある。
   - mozaic.fm と同じ provider・同じ NS で 10 秒失敗、30 秒成功という実測を引き継ぎ、初回は 30 秒、
     NXDOMAIN が再現した場合だけ 60 秒へ上げる現在の command が合理的である。tldr の「30 秒よりさらに」
     と command の 30 秒という不整合も解消すること。
   - 18 identifiers は Let's Encrypt の 1 certificate あたり 100 identifiers の上限内である。
     [Let's Encrypt Rate Limits](https://letsencrypt.org/docs/rate-limits/)

2. **major: reconfigure 成功後に保存された renewal option を検査する**
   - staging test 成功時だけ新しい option を保存するという契約は正しい。
     [Certbot User Guide](https://eff-certbot.readthedocs.io/en/stable/using.html#modifying-the-renewal-configuration-of-existing-certificates)
     ただし本 plan は、成功時に何が保存されたかを確認せず、そのまま production force renewal へ進む。
   - 手順 4 の直後に `/etc/letsencrypt/renewal/jxck.io.conf` を確認し、少なくとも
     `authenticator = dns-cloudflare`、credentials path、実測 propagation seconds、
     `preferred_profile = shortlived`、18 domains が維持されていることを acceptance に入れること。
     「shortlived は変更しない」という本 plan の境界を実測で守る gate でもある。

3. **major: force renewal / reload 後に disk と live の同一性を確認する**
   - 現案の `openssl s_client` は配信証明書の SAN / dates だけを見るため、force renewal で更新された
     `/etc/letsencrypt/live/jxck.io/fullchain.pem` を h2o が実際に読み直したことを証明しない。
     mozaic.fm 側で得た「disk 上と配信中の証明書を直接比較する」知見が抜けている。
   - force renewal 後・reload 前に disk 上の certificate の serial または SHA-256 fingerprint、dates、
     SAN を記録し、reload 後の `s_client` 出力と serial / fingerprint が一致することを確認する。
     これで `/keys/jxck.io` symlink、reload、実配信までを一続きで検証できる。

4. **minor: Cloudflare token の権限名を曖昧にしない**
   - zone ごとに token を分ける判断は妥当であり、侵害時の blast radius を jxck.io zone に限定できる。
   - Certbot 5.7.0 の dns-cloudflare plugin 同梱文書は API token に対象 zone の
     `Zone:DNS:Edit` を要求している。本文の `Zone:DNS:Edit + Read` は Cloudflare UI 上のどの Read 権限か
     不明確なので、実際に選ぶ permission 名を正確に書くこと。mozaic.fm token で必要だった権限セットを
     dashboard で確認し、追加の Read が実測上必要なら `Zone:Zone:Read` と明記する。不要なら
     least privilege のため外す。

5. **minor: rollback の対象に repo 側の手動 reissue 経路を含める**
   - 現在の rollback は renewal conf を webroot に戻すだけで、手順 7 後の
     `admin.jxck.io/cert-jxck.sh` は dns-cloudflare のまま残る。rollback の完了条件を
     「自動更新だけ webroot に戻す」とするのか、「手動経路も含めて移行前へ戻す」とするのかを明記し、
     後者なら script の変更も revert 対象に含めること。
   - DNS-01 で発行済みの証明書自体は authenticator 情報を配信時に必要としないため、authenticator を
     webroot に戻すだけなら証明書の再発行は不要である。

6. **minor: repo 変更の acceptance を追加する**
   - `admin.jxck.io/cert-jxck.sh` の現物は plan 記載どおり webroot option、18 個の `-d`、
     `--preferred-profile shortlived` を持ち、AGENTS.md 上もこの standalone script に別の build gate はない。
   - 更新後に `bash -n admin.jxck.io/cert-jxck.sh`、webroot option が消えたこと、dns-cloudflare の
     credentials / 実測 propagation seconds が入ったこと、18 個の `-d` と shortlived が維持されたことを
     diff と機械的な件数確認で検証する。secret は repo に入れず path だけを commit する。
