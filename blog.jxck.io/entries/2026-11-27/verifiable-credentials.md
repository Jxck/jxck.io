# [verifiable credentials][security] Verifiable Credentials による個人情報収集の最小化

## Intro

マイナンバーカードや JPKI を用いて本人確認する方式への移行が急がれている。

しかし、確認方法が変わっても、そこで取得した情報を DB に保存していては、漏洩のリスク自体はなくならない。

個人情報自体を渡さずに、必要な確認を行うことができれば、そのリスクも減らせるだろう。

ここで活用が期待されているのが、Verifiable Credentials だ。

この記事は、[サイバーセキュリティアドベントカレンダー](https://qiita.com/advent-calendar/2026/cyber-security-by-jxck) 4 日目である。


## 情報の「収集」と「確認」

従来は、成年であるかを確認するために、生年月日が確認できる公的文書を提示していただろう。

お酒を買うときに免許を提示するようなアレだ。

eKYC でも同様に、生年月日を収集する必要があった。

しかし、ゲームの利用で年齢だけを確認する場合、必要なのは over 18 であるかどうかの boolean だ。

生年月日を収集するのは、情報が多すぎるのだ。

同様に、学割のための「学生である」、マチアプのための「未婚である」なども boolean で良く、住民票や学生証自体が必要なわけではないという場面も多々あるだろう。

こうした場合に、その事実の証明だけを取得し、その真正性を確認する方法として活用できるのが Verifiable Credentials だ。


## Verifiable Credentials

マイナンバーカードは、基本 4 情報を提供することができる。

- 氏名
- 住所
- 生年月日
- 性別

これらの情報は mdoc という方式で iPhone や Android の Wallet に格納することが可能だ。

この mdoc は、J-LIS (地方公共団体情報システム機構) という組織によって署名されているため、J-LIS の公開鍵を取得すれば、署名を検証して改ざんされていないかを確認できる。

例えば、マッチングアプリの利用を 18 歳以上に制限する場合、マチアプ事業者は Wallet からこの mdoc を読み出し、生年月日を確認することになる。

このとき、マイナカードから読み出し、検証ができるこの mdoc こそが、広義の Verifiable Credentials そのものなのだ。

一方これとは別に、W3C は Verifiable Credentials という標準仕様を定めている。この W3C/VC に準拠したものを狭義の Verifiable Credentials と呼ぶことにする。

- Verifiable Credentials Data Model v2.0 | W3C
  - https://www.w3.org/TR/vc-data-model-2.0/

今回は、どういうフォーマットを使っているか自体はあまり問題ではないため、広義の VC について話していく。


## Selective Disclosure

署名を検証するとなると、メッセージ全体に署名して、全体を検証しないといけなくなる。

基本 4 情報の場合、以下がメッセージ全体となるイメージだ。

```json
{
  "name": "Jxck",
  "address": "Mars",
  "birthday": "1900-01-01",
  "sex": "N/A"
}
```

J-LIS がこのメッセージに署名し、それを Wallet に保存する。

マチアプには、Wallet からこのメッセージ全体を提出し、マチアプはサーバ側で J-LIS の公開鍵を取得して検証する。

となると、「成年かどうか」を知りたいだけなのに、基本 4 情報を全部渡すことになってしまう。

しかし、mdoc は署名の検証を可能にしながらも、生年月日だけをマチアプに提出することができる。

生の値に署名するのではなく、それぞれの salt 付きハッシュ値に対して署名するイメージだ。

```json
{
  "sd":[
     sha256(salt1 + "name" + "Jxck"),
     sha256(salt2 + "address" + "Mars"),
     sha256(salt3 + "birthday" + "1900-01-01"),
     sha256(salt4 + "sex" + "N/A")
  ]
}
```

これだけを見ても、ハッシュが 4 つあるだけで、中身はわからない。

ただし、メッセージ全体の署名は検証できるので、値が改ざんされていないことはわかる。

Wallet は、これと合わせて以下のように、開示したい値だけを salt とともに提供する。

```
[salt3, "birthday", "1900-01-01"]
```

マチアプ事業者は、このハッシュを計算し、それがメッセージの `sd` 配列の中にあるかどうかを見れば良い。

メッセージは改ざんされていなかったため、開示された値は正しい、つまり生年月日がウソではないことがわかるのだ。

他の項目は、salt がわからない上にハッシュ値だけなので、逆算して取り出すことができない。

このように、署名されたメッセージ全体から、選択的に値を開示するのが Selective Disclosure (選択的開示) だ。


## over 18 VC

選択的に開示することができたが、まだ生年月日を開示する必要がある。

ここから、「成年証明」を可能にするには、2 つの方法がある。

1. 発行側が `over 18` 項目を取得できるように追加対応する
2. 生年月日から `over 18` を導出できるようにする

前者は簡単だ。J-LIS が生年月日情報を保証しているのだから、一緒に `over 18` を証明すれば良い。Wallet はその項目だけを選択して開示すれば済む。

```json
{
  "sd":[
     sha256(salt1 + "name" + "Jxck"),
     sha256(salt2 + "address" + "Mars"),
     sha256(salt3 + "birthday" + "1900-01-01"),
     sha256(salt4 + "sex" + "N/A"),
     sha256(salt5 + "over18" + true)
  ]
}
```

もちろん、これには発行側の対応が必要だ。

一方、後者は発行側が実装を変えなくても、Wallet 側で対応できる。

ところが Wallet が勝手に「over 18」を宣言したところで、本当かどうか信用できない。

ここで必要なのは「生年月日は見せないが、J-LIS が署名した生年月日を保持し、それが 18 歳以上であることを証明する」という命題であり、これを実現するのが「**ゼロ知識証明**」なのだ。

```json
{
  "over18": true,
  "zkp": "..."
}
```

マチアプは、この証明を検証することで、18 歳以上であることを、生年月日を得ずに確認できる。

ところが、現状はどちらの方法も普及の途中だ。

前者については、対面でアプリを使う際に、生年月日を表示せずに「20 歳以上かどうか」だけを確認する方法として公式に提供されている。

- スマートフォンのマイナンバーカードを確認する方法 | マイナンバーカード対面確認アプリ
  - https://services.digital.go.jp/mynumbercard-check-app/guide/check-mynumbercard-iphone/
- 生年月日を伝えずに、学園祭の「20 歳未満の飲酒防止」を、より確実に。iPhone のマイナンバーカードを使った年齢確認の現場から | デジタル庁ニュース
  - https://digital-agency-news.digital.go.jp/articles/2026-10-27

しかし、対面のみで、しきい値も `over 20` に限られる。マチアプのようなオンラインの eKYC が `over 18` だけを受け取る、といった使い方はまだ提供されていないようだ。

後者のゼロ知識証明は、証明方法自体は確立していながら、それをこうした用途で使うための標準化が途上だ。


## VC の民間利用

VC は、別に誰が出しても良い。

例えば、ある大学が卒業証明を VC として発行し、卒業生が就活時に企業に提出する。企業は大学の公開鍵で、その卒業の真正性を検証する、といった用途が可能だ。

VC が標準化されたフォーマットであれば、対応する Wallet に入れることができる。

このように、証明したい情報を、各 Issuer が VC として発行するようになれば、様々な物が検証可能な証明として運用できるのだ。

想定される VC には様々な物がある。

- 警察が有効な運転免許の保持だけを証明する VC を発行する
- 試験ベンダーが資格取得を示す VC を発行する
- イベントサイトがチケットを VC として発行する
- Google や Apple などが、普段の利用状況からその人が Bot で無いことを証明する VC を発行する

このとき、例えば「何年卒業なのか」を隠しつつ「卒業した」という事実だけを選択的に開示できる VC を提供するといったことは、大学が決めることができる。企業は、それで足りると思うのであれば、必要以上の情報を収集しないで済むのだ。

また、VC は「Issuer を信用できる」ならそれで良い。

例えば、身元の保証を代行するベンダーが現れ、ユーザがマイナカードで生年月日を登録したとする。これを確認したベンダーが `over 18` であることを VC として発行するサービスを、デジタル庁の認証を得て提供したとしよう。

マチアプは、そのベンダーを信頼するのであれば、その VC を受け入れて成年判定ができ、生年月日はベンダーに集約できる。すべてが公的な Issuer でないといけないわけではないため、全部がデジ庁の実装待ち、というわけではない。

もちろん、事業者によっては生年月日そのものを集める必要があるが、「集めたくない」ケースでは最小限の情報を、信頼できる Issuer が発行した VC によって収集するといった運用が期待できるのだ。


## Holder Binding

タイムズから券面画像が漏洩した際、「それを悪用して金融サービスに勝手に登録される恐れ」などのリスクが取り沙汰された。(本当にタイムズのせいで発生したかは、因果の証明を含めて判断が難しいが)

実は同じリスクは、金融サービス事業者側にもある。「券面画像」が提示されたとして、それが本当に「本人のもの」なのかを確認するのは難しいからだ。たまたま似た顔の人の券面画像を、ダークウェブで買ってきただけかもしれない。

そして、金融サービスが起因で生じた損害は、基本的に金融サービス側が負担することになる。「勝手にカードを作られて使われた」という攻撃が発生しても、金銭的な被害に遭うのは「勝手に作られた人」ではなく「カード会社」になるだろう。

大規模な漏洩が発生すると、「本人の確認」と信じて使ってきた手法が、「本人確認手段として不十分」になってしまうため、情報を漏洩された消費者だけでなく、そこにサービスを提供している他の金融サービスにも、間接的な影響を及ぼすことになる。

一方、VC には Holder Binding という仕組みがあり、保持している本人以外が盗んで提示したら、すぐにバレるようになっている。

つまり、仮に事業者が保持していた VC が漏洩したり、マルウェアによって Wallet から盗まれたりしても、それを使って年齢や学歴を詐称するといったことができないのだ。

ただの写真や紙の書類と、VC の大きな違いはそこにある。


## まとめ

VC の普及のネックは、それを入れておく Wallet の普及だった。

しかし、iPhone や Android に Wallet が入ったおかげで、発行された VC を保持するための基盤はかなり整った。

今後は、様々な Issuer が VC を発行し、それを持ち運び、必要に応じて最小限の提示をするといったことが、一般的になっていくだろう。

タイムズが VC で「有効な免許を保持している」という情報だけを集め、免許番号まで収集しなくて良くなるかは制度次第だが、年齢確認などのユースケースはどんどん置き換えていけるだろう。

こうして、事業者が集める情報を最小限にすることは、漏洩時の被害の最小化に繋がると期待される。
